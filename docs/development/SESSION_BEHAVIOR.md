# Session Behavior

## Overview
Phase 6 introduces deterministic multi-turn session handling that supports:
1. Persisted chat sessions and messages.
2. Bounded follow-up context resolution.
3. Optional threshold-based session summarization.
4. Session lifecycle transitions (`active`, `archived`, `expired`).
5. Transcript export/import for deterministic round-trip portability.

Primary implementation modules:
- `src/farmer_helper/schemas/session.py`
- `src/farmer_helper/repositories/chat_session_repository.py`
- `src/farmer_helper/services/session/context_resolver.py`
- `src/farmer_helper/services/session/summarizer.py`
- `src/farmer_helper/services/session/lifecycle_service.py`
- `src/farmer_helper/services/session/transcript_service.py`

## Data contracts
Core schema groups:
- Session and message payloads (`ChatSession*`, `ChatMessage*`).
- Follow-up context request/response (`FollowUpContextRequest`, `FollowUpContextResponse`).
- Summarization request/response (`SessionSummaryRequest`, `SessionSummaryResponse`).
- Transcript request/response (`SessionTranscript`, `TranscriptImportRequest`, `TranscriptMessage`).

Role and status values are constrained to stable literals:
- Message role: `user` or `assistant`.
- Session status: `active`, `archived`, or `expired`.

## Lifecycle behavior
Session lifecycle operations are deterministic and repository-backed:
1. Session creation starts in `active` status by default (or explicit status when importing).
2. Archive operation transitions a session from any current state to `archived`.
3. Expiry operation transitions stale `active` sessions to `expired`.
4. Session/message read operations are key-based and preserve insertion order for history replay.

Lifecycle orchestration lives in `SessionLifecycleService` and uses repository methods to ensure consistent persistence semantics.

## Follow-up context resolution
`FollowUpContextResolver` builds bounded context windows from persisted history.

Deterministic guarantees:
1. Context only includes session messages from the requested session key.
2. Window size is bounded by `max_turns` and optional `max_messages`.
3. Returned ordering is stable by turn index.
4. Roles are narrowed to the session role literal set.

This context can be prepended to retrieval and answer-generation question text for follow-up turns.

## Summarization behavior
`SessionSummarizer` provides optional deterministic summarization metadata for long sessions.

Behavior:
1. Summarization is activated when message count crosses a configured threshold.
2. Summary points are bounded (`max_points`) and generated by deterministic extraction logic.
3. Output contains both `summary` text and `highlights` for downstream display/use.

This component is intentionally rule-based to preserve repeatability for tests and debugging.

## Transcript export and import
`SessionTranscriptService` supports portable deterministic transcript workflows.

Export:
1. Resolve session by key.
2. Read message history in order.
3. Return `SessionTranscript` containing session metadata and ordered `TranscriptMessage` items.

Import:
1. Resolve target session key (`session_key_override` if provided, otherwise transcript key).
2. Reject import if target session key already exists.
3. Create a new session (status preserved from transcript).
4. Rehydrate messages in transcript order with original role/content/metadata.
5. Return the imported `SessionTranscript` for verification.

Operational constraints:
- Import is intentionally non-destructive and does not merge into existing sessions.
- Duplicate-target imports fail fast with `ValueError`.

## Extension points
Phase 6 provides clear seams for future memory policy upgrades:
1. Context strategy extension:
   - Replace or wrap `FollowUpContextResolver` to support richer selection/ranking.
2. Summarization strategy extension:
   - Swap deterministic summarizer logic with policy-aware extractive or model-assisted approaches.
3. Lifecycle policy extension:
   - Extend expiry/archive criteria (for example inactivity windows, retention classes, or per-user policy).
4. Transcript transport extension:
   - Add alternate transcript serializers/versioning while preserving schema contracts.

Recommended rule for extensions:
- Keep schema-level contracts stable.
- Add new behavior behind service-level interfaces and deterministic defaults.
- Preserve existing tests and add focused regression coverage for policy-specific branches.
